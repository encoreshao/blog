# Material Check (read before drafting)

An article only holds together when it's built from real, checkable material — not padding, not a fabricated incident, not a generic restating of the topic. This matters more for this skill than for most writing, because every article starts from a URL, not from something Encore actually lived through.

## Take an inventory before writing a word

List, internally, at least five concrete things pulled from the fetched source: named details, numbers, exact steps, direct quotes, code, error messages, version numbers, benchmark results, dates, outcomes. "It's a tool for X" is a category, not a piece of material — it can't anchor a paragraph on its own.

If the source can't produce five concrete details, that's a signal, not a problem to write around. Read more of the source first — the actual README, the code, the linked issue, not just the summary paragraph at the top. If there still isn't enough after that, shrink the target length instead of padding. A tight 500-word piece beats a stretched 1200-word one built on restated points and "many developers face this" generalities.

## Don't ghostwrite an experience nobody had

The fetched source describes a tool, project, or idea — it is not a transcript of something Encore did. The workflow's structure calls for opening with "a moment, not a thesis," which works when Encore actually lived that moment. Applied blindly to a URL he just read, it produces a fabricated anecdote: an invented 2am debugging session, an invented error message, an invented teammate reaction. A specific-sounding detail that turns out to be invented reads as more artificial than a vague one, not less — precision is only convincing when it's true.

When there's no real personal incident to open with:

- Frame the moment honestly: what made you open this repo or page, what question you had, what you found when you actually read it. "I opened the repo because X" is fine when X is a real, plausible, generic reason — curiosity, a recommendation, a problem you were already circling.
- Only claim to have run or tried something if that's actually true. Open-source code you can reasonably describe reading or reasoning through is fair game; a hosted SaaS product or a paper's claimed benchmark is not something to claim firsthand results for.
- If the piece is more of a "here's what this project does and why it's interesting" walkthrough than a "here's what happened to me" story, let it read that way. An honest explainer beats a dishonest anecdote.

## Ask instead of inventing

If genuine personal experience would make the piece meaningfully better — the user actually used the thing before asking for an article about it — ask one direct question before drafting: "Did you use this yourself, or is this from reading about it?" Skip the question when the answer is obvious from context (a paper just posted today, a tool the user is clearly encountering for the first time via the URL they pasted).

## Keep time-sensitive claims honest

Version numbers, pricing, "in beta" status, and compatibility claims drift. State only what the source confirms as of the fetch date. Don't round a "we're planning to support X" into "it supports X."
